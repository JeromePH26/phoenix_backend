# 04 – Probability Calibration & Uncertainty / Confidence

Scope: probability calibration and uncertainty/confidence handling in **both** the live
football pipeline and the Model Lab (self-learning engine V0). Read against
`Claude AN2.txt` §14 (market-specific calibration), §22 (data quality as a real model
component), §23 (uncertainty as first-class), §40–41 (metrics; not hitrate).

## TL;DR

- **There is no probability calibration anywhere.** No isotonic, no Platt/logistic, no
  temperature scaling, no beta calibration – not in the live pipeline, not in the Model
  Lab, not in any challenger engine. `grep -riE "isotonic|platt|temperature|calibrat"`
  over `lib/` returns only *calibration-curve measurement* code, never a calibration
  *transform*. Raw independent-Poisson / Monte-Carlo probabilities are published as-is.
- The only "regularisation" that exists is **input shrinkage** on goal rates and team
  strengths toward a league/global prior (`football_engine_input_service.dart`,
  `weight_config.dart`, `team_strength_engine.dart`). That is a prior on λ inputs, not a
  calibration of output probabilities. It is genuinely implemented and reasonable.
- The user-facing **"Vertrauen / confidence"** number is a hand-weighted 0–100 heuristic
  (`_trustScore`, `football_market_selection_service.dart:498`). It is **not** a
  probability and has no calibration guarantee.
- **"Stabilität"** is a dead field for football. `simulation['stability']` is never
  produced by `football_simulation_service.dart`; only `football_finalization_service.dart:53`
  and `baseball_service.dart` read/emit it. For any football tip it is absent → renders 0.
- **Uncertainty propagation vs §23: mostly absent.** Of the 8 signals §23 lists, only
  *data quality*, *sample size (goal rates)* and *xG availability* feed anything, and only
  into the `_trustScore` heuristic – never into the probabilities, the fair odds, or a
  credible interval. Model spread / challenger spread / league experience / historical
  calibration are not propagated at all.
- **Bootstrap** (`Metrics.pairedBootstrap`, `metrics.dart:94`) is a paired percentile
  bootstrap on per-match Brier differences: 2000 resamples, fixed seed 42, 95% CI,
  verdict by whether the CI straddles 0. Mechanically sound and correctly *paired*; weak
  points are selection-then-test over many challengers, single metric (Brier only), fixed
  RNG stream, and combining holdout + shadow diffs into one resample pool
  (`monthly_review_service.dart:179`).
- **Metrics present:** Brier (multi/binary), log loss, argmax accuracy, avg top
  probability, calibration *buckets* (argmax-only), paired bootstrap CI on Brier, plus a
  separate published-tips ROI/yield on the settlement side. **Missing:** ECE (buckets
  computed, never aggregated), reliability of non-argmax classes, CLV, max drawdown,
  Brier skill score vs a baseline, per-confidence-bucket ROI, calibration as a promotion
  gate.
- **`draw_no_bet_*` Brier ≈ 0.63 is not a hard market and not a calc crash – it is a
  metric-encoding artefact.** In the Model Lab, DNB is scored as a **3-class** market with
  the *identical* probability vector and *identical* one-hot as `1x2`
  (`engine_replica.dart:304-335`, `learning_sample.dart:110-118`). Its Brier is therefore
  mathematically equal to the `1x2` Brier on the same samples, and ~0.63 is roughly the
  expected value of a 3-class Poisson 1X2 Brier (uniform baseline = 0.667). Meanwhile the
  **live** pipeline models DNB as a 2-outcome conditional market
  (`football_simulation_service.dart:222-229`). Live and Lab disagree on what DNB even is.

## Calibration today (live + model lab)

### Live pipeline

Flow: `football_engine_input_service` (normalise λ) → `football_simulation_service`
(100k Monte-Carlo independent Poisson draws) → `football_market_selection_service`
(pick market) → `football_daily_pipeline_service` (publish) /
`football_finalization_service` (legacy admin endpoint).

- Probabilities are raw simulation frequencies: `homeWins / simulations` etc.
  (`football_simulation_service.dart:211-217`). No post-hoc transform is applied before
  they become `probabilities` / `fairOdds` in the published payload
  (`football_simulation_service.dart:273-309`).
- Draws are generated by **independent** home/away Poisson (`_samplePoisson`,
  `football_simulation_service.dart:433`). Independent Poisson systematically
  under-predicts 0:0/1:1 and therefore the draw class – a well-known 1X2 miscalibration
  that nothing corrects. Dixon-Coles τ exists (`poisson_math.dart:40`) but only as a
  Model-Lab *challenger* (`ModelEngine.dixonColes`, `engine_replica.dart:420`); the live
  champion runs `rho = 0`.
- If a promoted league champion existed, its learned class probabilities would be merged
  in verbatim (`_mergeLearnedProbabilities`, `football_simulation_service.dart:401`) –
  still no calibration layer. (No league champion is currently promoted;
  `promotionEnabled` default `false`, `model_lab_config.dart:153`.)
- Input-level shrinkage IS applied and is the closest thing to regularisation:
  - Goal rate → league baseline → global baseline, factor `n/(n+8)` and `n/(n+50)`
    (`football_engine_input_service.dart:23`, `:31`, `:273-313`).
  - Model-Lab weight shrinkage `n/(n+150)` (`weight_config.dart:46`,
    `model_lab_config.dart:170`).
  - Team-strength IPF fit shrunk toward neutral each iteration
    (`team_strength_engine.dart:152-155`, `:237`).
  These shape λ; they never touch P(outcome).

### Model Lab

- `MarketEvaluationResult.compute` (`walk_forward_evaluator.dart:121`) evaluates an engine
  and records Brier / log loss / accuracy / calibration buckets. It **measures**
  calibration (`Metrics.calibrationBuckets`, `metrics.dart:60`) but never fits or applies
  one.
- `calibrationBuckets` only bins the **argmax** class probability and asks "did the
  argmax hit" (`walk_forward_evaluator.dart:176-188`). Bucket edges start at `0.50`
  (`metrics.dart:63`), so any match whose top class is < 50% (common for 3-class 1x2 /
  dnb) is silently dropped from the calibration view. Non-winning classes are never
  calibration-checked.
- `GlobalGoalsV1Engine`, `GlobalMarketEngine`, `DixonColesEngine`, `TeamStrengthEngine`:
  none contain a calibration step (`grep` over each file). They differ only in how λ is
  derived; the market probabilities all go back through the same
  `EngineReplica.evaluateGoals` Poisson math.

**Answer to Q1:** none. Not live, not Model Lab, not in evaluation. Plainly: PHÖNIX today
publishes uncalibrated model probabilities and does not even score calibration error
numerically (only draws buckets).

## "Confidence" & "Stability": how computed

### "Vertrauen" (confidence / trust score)

Computed once, in `FootballMarketSelectionService._trustScore`
(`football_market_selection_service.dart:498-525`), as a weighted sum, max 100:

| component | weight | source |
|---|---|---|
| best market probability (`p*100/100 * 35`) | 35 | model probability of the picked market |
| gap of selection score to 2nd market (`/25 * 20`) | 20 | `bestProbability - secondProbability` (`:346-353`) |
| data quality (`dq/100 * 30`) | 30 | `simulation['dataQuality']` |
| simulation count (`sims/100000 * 10`) | 10 | `simulation['simulations']` (0 → 0 pts) |
| real xG available | 5 | `goalExpectations['realXgAvailable']` |

Then in the live publish path (`football_daily_pipeline_service.dart:356-363`):
`confidence = trustScore + contextConfidenceDelta`, where `contextConfidenceDelta` is
always `0` because `aiContext['applied']` is structurally never `true` (Gemini context
step is deliberately unwired – comments at `football_market_selection_service.dart:434`,
`football_simulation_service.dart:320`). The legacy admin endpoint
`football_finalization_service.dart:29-31` does the same with a `phaseFour.confidenceDelta`
that is likewise never produced.

So **displayed confidence == `_trustScore`**. It is a heuristic on a 0–100 scale, not a
probability, never compared against realised frequencies, and its weights are hand-set
(the file itself calls out "Kein künstlicher Mindestwert mehr", i.e. it has been tuned by
hand more than once).

Can it be low while a tip is still issued? **Yes.** Since the 2026-08-26 change
("jedes Spiel soll einen Tipp haben"), `phoenixTip` / `analysisLead` is always shown
(`football_market_selection_service.dart:427-431`, `football_daily_pipeline_service.dart:340-352`).
`qualifiesForTip` (needs `dataQuality >= 60`, `trustScore >= 60`, `simulations > 0`,
`p >= minimumProbability`) only gates whether it counts as a **Value/bet recommendation**
and enters ROI (`football_market_selection_service.dart:373-377`). A tip with trust 35 is
published as "PHÖNIX-Tipp mit geringerer Sicherheit" (`:445-446`).

### "Stabilität 0/100"

- **Football: not computed.** `football_simulation_service.dart` never emits a
  `stability` key. `football_finalization_service.dart:53` copies `simulation['stability']`
  into the final payload; it is `null`/absent, so any downstream renderer that coerces to
  int shows **0**.
- The concept exists only for other sports: `baseball_service.dart:388`
  (`100 - (high-low)*500`, a CI-width proxy) and `tennis_math_engine.dart:235`
  (`_stability`). Football has no analogue wired.
- Net: "Stabilität 0/100" on a football tip means "this metric was never calculated",
  not "this tip is maximally unstable". It is tech debt / a misleading UI field.

## Uncertainty propagation vs AN2 §23

§23 asks the engine to also answer "how trustworthy are these 64%?" using: sample size,
data coverage, league experience, lineup status, missing xG, model spread, historical
calibration, challenger spread. Current state:

| §23 signal | propagated? | where / gap |
|---|---|---|
| Sample size | partial | shrinks λ toward baseline (`football_engine_input_service.dart:158-172`); also 20 pts of trust via `simulationCount` (a fixed 100k, so effectively binary present/absent). Team-game count feeds shrinkage only, not an interval. |
| Data coverage / quality | partial | 30 pts of `_trustScore`; also a hard publish gate `dataQuality >= 50/60`. Never widens the probability or the fair odds (violates §22: DQ must affect *Unsicherheit*, *Value-Anforderungen*, *Modellgewichtung* – it affects none of those, only a display score + gate). |
| League experience | no | league baseline is blended into λ (`leagueAwareBaseline`, `:299`) but "how much history this league has" is not surfaced as uncertainty. |
| Lineup status | no (display only) | `trust.components.lineupConfirmed` and a warning string (`football_market_selection_service.dart:407`, `:448`). §21 ("Lineup fehlt → Unsicherheit erhöhen") is not implemented – probabilities are identical with or without a confirmed lineup. |
| Missing xG | partial | 5 pts of `_trustScore` + `sourceType` flag + warning. λ still computed from goal averages; no variance inflation. |
| Model spread (ensemble disagreement) | no | single Monte-Carlo run per fixture, single λ. No ensemble, no spread. |
| Historical calibration | no | never fed back; calibration buckets are written to `phoenix_model_evaluations.calibration` and not read by anything that predicts. |
| Challenger spread | no | challengers produce shadow predictions; their dispersion vs champion is never turned into a per-fixture uncertainty. |

There is **no credible/confidence interval on any published probability** anywhere in the
codebase (`grep -riE "credible|interval"` → only `CalibrationBucket` bounds and the
bootstrap CI on aggregate Brier). The Model Lab `EngineReplicaOutput` carries a single
`usedFallbackBaseline` bool (`engine_replica.dart:31`) – the entire per-prediction
uncertainty vocabulary.

## Bootstrap comparison methodology

`Metrics.pairedBootstrap` (`metrics.dart:94-154`), called from
`ChampionChallengerComparison.compare` (`walk_forward_evaluator.dart:248-321`) and
`MonthlyReviewService` (`monthly_review_service.dart:187-193`).

**What it does**
- Statistic: **mean of per-match Brier loss differences** `challengerBrier[i] - championBrier[i]`
  (`walk_forward_evaluator.dart:300-303`). Negative ⇒ challenger better.
- **Paired**: yes, correctly. Both engines are evaluated on the exact same, identically
  ordered `comparableSamples` list; a sample either side cannot score is dropped for both
  (`walk_forward_evaluator.dart:264-270`). `diffs[i]` indexes both `perSampleBrier` arrays
  positionally.
- Resampling: `resamples = 2000` (`model_lab_config.dart:200`), each draw is `n` iid
  picks with replacement from `diffs`, store the resample mean.
- CI: **percentile method**, `lowerIndex = floor(0.025*2000) = 50`,
  `upperIndex = floor(0.975*2000) = 1950` on the sorted resample means
  (`metrics.dart:123-131`). No BCa, no bias/skew correction, no studentisation.
- RNG: `Random(randomSeed ?? 42)` – callers never pass a seed, so **every bootstrap uses
  the identical fixed stream**. Reproducible, but there is no Monte-Carlo-error estimate
  and no sensitivity check.
- Verdict (`metrics.dart:138-145`):
  `upper < 0` → `challengerClearlyBetter`; `lower > 0` → `championBetter`;
  straddles 0 → `approximatelyEqual`; `n < minSampleSize` → `notEnoughData`.
  `minSampleSize = minValidationSample = 40` in the walk-forward/holdout path;
  `MonthlyReviewService` passes `1` and gates separately on
  `minPromotionSample = 120` (`monthly_review_service.dart:191`, `:240`).
- Promotion (`monthly_review_service.dart:245-264`): only `challengerClearlyBetter`
  + `combinedSample >= 120` + `promotionEnabled` triggers an automatic promotion. Default
  `promotionEnabled = false`.

**Is it sound?** Mechanically, mostly yes: paired, correct percentile indexing, a
sensible "CI excludes 0" decision rule (≈ two-sided α=0.05 test on ΔBrier). Concerns:

1. **Selection then test.** `MonthlyReviewService` picks the challenger with the *lowest*
   `meanDifference` across all challengers for that league×market
   (`monthly_review_service.dart:206-215`), then bootstraps *that one*. Testing the
   winner of a search inflates the false-positive rate – exactly the "zufällig starkes
   Wochenende" risk §43 warns about. Mitigated only by n≥120 and the env flag.
2. **Single metric.** Only Brier gets a CI. Log loss, calibration and ROI get no
   uncertainty. §42 wants "bessere Calibration" + "stabile Ergebnisse" as gates; neither
   is bootstrapped.
3. **Pooling two populations.** `monthly_review` concatenates holdout backtest diffs and
   live shadow diffs into one vector before resampling
   (`monthly_review_service.dart:179-185`). These have different data-generating
   conditions; a plain pooled bootstrap understates between-source variance.
4. **Percentile bootstrap on small, skewed, discrete ΔBrier** (n often 40–120). Coverage
   can be off; BCa or a sign/permutation test would be more defensible at "expert level".
5. **Fixed seed** removes resampling variability from view – fine for reproducibility,
   but no one can see how stable the CI itself is.
6. **Silent sample attrition** for GLOBAL_GOALS_V1 / GlobalMarket challengers: samples
   without a Phase-2 snapshot are dropped for both sides
   (`walk_forward_evaluator.dart:264-270`), so those comparisons run on a
   recent-fixtures-only subset that may not represent the league.

## draw_no_bet Brier ~0.63 investigation

**Observation to explain:** `draw_no_bet_home` / `draw_no_bet_away` holdout Brier ≈ 0.63
for champion *and* challengers, n = 116 – "abnormally bad for a near-binary market".

**Encoding trace:**

1. `LearningMarket.drawNoBetHome/Away` report `isMultiClass == true`
   (`learning_market.dart:33-36`), so they are scored with `Metrics.brierMultiClass`
   over **3 classes** (`walk_forward_evaluator.dart:154-162`,
   `shadow_prediction_service.dart:286-294`, `:351-359`).
2. `EngineReplica.evaluateGoals` for `drawNoBetHome` returns
   `classProbabilities = [P(home), P(draw), P(away)]` with labels `[won, push, lost]`
   (`engine_replica.dart:304-319`); `drawNoBetAway` returns the same vector permuted to
   `[P(away), P(draw), P(home)]` (`:320-335`).
3. `LearningSample.outcomeIndexFor(drawNoBetHome)` returns `0` if home win, `1` if draw,
   `2` if away win – **byte-for-byte identical to `oneXTwo`** (`learning_sample.dart:76-81`
   vs `:110-113`). `drawNoBetAway` is the consistent mirror (`:114-117`), matching the
   permuted probability vector.
4. `Metrics.brierMultiClass` is `Σ (p_i - y_i)^2` over the 3 classes (`metrics.dart:14-25`)
   – **sum form, range 0…2**, not divided by K.

**Consequence:** for a given engine on a given sample set,
`Brier(draw_no_bet_home) == Brier(1x2)` exactly (same probabilities, same one-hot), and
`Brier(draw_no_bet_away)` is the same value (a permutation of both vectors leaves the
squared-error sum unchanged). All three markets must report the identical mean Brier on
identical holdout samples.

**Is 0.63 abnormal?** No. Rough expectation for a 3-class independent-Poisson 1X2
forecast: with typical P ≈ (0.45 home, 0.27 draw, 0.28 away), the outcome-frequency-
weighted Brier ≈ `0.45·0.454 + 0.27·0.814 + 0.28·0.794 ≈ 0.65`. The uniform-guess 3-class
baseline is `6/9 = 0.667`. A competent bookmaker 1X2 (sum-form) Brier is ≈ 0.57–0.59; a
plain Poisson model ≈ 0.60–0.62. **0.63 = a mediocre, uncalibrated 3-class 1X2 model**,
which is precisely what the live champion is (independent Poisson, `rho = 0`, no
calibration, goal averages instead of xG).

**So which is it – metric bug, hard market, or calibration failure?**
Primarily a **metric-encoding / market-definition inconsistency**, with a secondary real
calibration weakness:

- Not a crash/formula bug: `brierMultiClass`, `outcomeIndexFor`, and the label vectors are
  internally consistent (drawNoBetAway is correctly mirrored, not swapped).
- It **is** misleading: DNB in the Model Lab is a relabelled full 1X2, scored on the 0…2
  three-class scale, and then displayed next to genuinely binary markets (`btts` ≈ 0.24,
  `over_under_2_5` ≈ 0.24–0.25) whose Brier lives on the 0…1 scale. Reading "0.63" as
  "DNB is broken" is the misconception the encoding invites.
- It **contradicts the live engine**, which models DNB as a 2-outcome market conditional
  on no draw: `dnbHome = P(home)/(P(home)+P(away))`
  (`football_simulation_service.dart:222-229`, and `_mergeLearnedProbabilities`
  `:417-424`). Live and Lab are scoring different quantities under the same name.
- The residual real signal: because the shared 1X2 model is uncalibrated and
  draw-under-weighted (independent Poisson), even a correct 2-class DNB Brier would be
  merely ok, not great.

**Recommended for the rebuild:** score DNB as a 2-class conditional market – drop push
matches (or treat push as a 0.5-credit), renormalise `[home, away]`, use `brierBinary` –
so it matches the live engine and is comparable to other binary markets. If a 3-way
won/push/lost view is wanted, report it on its own clearly-labelled 3-class scale and
never in the same column as binary Brier. Either way, n = 116 is far below
`minPromotionSample = 120` and dominated by noise; no decision should rest on it.

## Open questions for the rebuild plan

1. **Calibration layer (§14):** per-market isotonic or Platt/temperature on the score
   distribution outputs, fit on the Learning class, held out on Holdout. Where does it
   live – inside the Match-State→Markets step of the new pipeline, or a post-processor
   shared by live + Model Lab? It must be the *same* code both sides, unlike DNB today.
2. **DNB / DC definition:** freeze one definition (recommended: DNB = 2-class conditional)
   and use it in `engine_replica.dart`, `shadow_prediction_service.dart`,
   `football_simulation_service.dart`, and the metrics column simultaneously.
3. **Confidence redesign (§22/§23):** replace `_trustScore`'s hand-weights with something
   grounded – e.g. a predicted Brier / predicted calibration error per fixture from
   (sample size, coverage, lineup, xG availability, ensemble spread, challenger spread),
   and let it actually move value thresholds and model weighting, not just a badge.
4. **Per-prediction uncertainty object:** decide the representation – a credible interval
   on each market probability (from Monte-Carlo resampling of λ + parameter posterior),
   or a scalar reliability. `EngineReplicaOutput` currently carries only
   `usedFallbackBaseline`.
5. **Kill or implement "Stabilität":** either compute a real football stability metric
   (CI width of the Monte-Carlo probability, or challenger dispersion over time) or remove
   the field from payload and UI.
6. **ECE + calibration as a promotion gate (§42):** aggregate the existing buckets into
   ECE, bootstrap it, and require "not worse on calibration" alongside "better on Brier".
7. **Bootstrap upgrade:** move to BCa or a permutation test for ΔBrier; correct for
   multiple challengers (e.g. only test the pre-registered hypothesis, or apply a
   step-down correction); separate holdout vs shadow instead of pooling; add ROI / log
   loss / ECE CIs.
8. **Real walk-forward:** `ChronologicalSplit.steps` / `WalkForwardStep` are built but
   never iterated by `learning_run_service.dart` – the "walk_forward" evaluation type is a
   single train/validation split. Decide whether the rebuild needs true rolling/expanding
   windows (§34, §38) and wire them.
9. **Draw under-weighting:** make Dixon-Coles (or bivariate Poisson / a draw inflation
   term) a candidate for the *champion*, not just a shadow challenger, since it directly
   drives 1X2 + DNB + DC calibration.
10. **Feed calibration history back:** `phoenix_model_evaluations.calibration` is written
    and never read by a predictor. Close the loop or drop the storage.
